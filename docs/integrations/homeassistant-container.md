# Home Assistant Container в HomeAiCore

Нативный модуль `homeassistant.module` для HomeAiCore **0.1.209 и новее**.
Управляется существующими заданиями установки, запуска, остановки, перезапуска,
обновления и удаления. Отдельный Docker Compose и собственная сборка Home Assistant
для этой интеграции не нужны.

## Установка из интерфейса

1. Обновите **ядро и privileged helper** HomeAiCore до версии, поддерживающей этот профиль.
2. Откройте «Модули → Каталог», обновите каталог, выберите **Home Assistant**.
3. Подтвердите доступ к сети и устройствам сервера. Установка использует официальный
   upstream-образ, закреплённый по `sha256`, а не изменяемый тег `stable`.
4. Дождитесь успешного завершения задания. Успех означает, что контейнер работает
   и его HTTP-интерфейс ответил на проверку, а не только что `docker start` завершился.
5. В «Установленные» нажмите **Открыть Home Assistant** и создайте его отдельную
   учётную запись. По умолчанию адрес — `http://IP_СЕРВЕРА:8123/`.

Ссылка в интерфейсе использует имя сервера из адреса открытого HomeAiCore. За обратным
прокси может потребоваться LAN-адрес сервера. Токены и cookie HomeAiCore в эту ссылку
не передаются. Встраивание через iframe и авторизация Home Assistant через Core не реализованы.

## Платформа и безопасность

- Нативный **Linux amd64 или arm64**, Docker Engine **23+**; Docker Desktop отклоняется.
- TCP-порт **8123** должен быть свободен. Установщик не останавливает чужой сервис
  и не меняет правила firewall. Разрешайте доступ только из доверенной сети.
- В соответствии с upstream-профилем контейнер использует `network=host` и
  `privileged`. Это широкие права на хост, не обычная песочница модуля.
- Исключение зарезервировано **только** для ID `homeassistant.module` и репозитория
  `ghcr.io/home-assistant/home-assistant@sha256:...`. Обе ссылки при обновлении
  проверяются до изменения служб Docker. Обычные модули сохраняют прежние ограничения.
- Manifest обязан явно объявлять `host.network` и `host.privileged`; UI показывает
  отдельное подтверждение при установке, включая установку через JSON manifest.
- Контейнер не получает `docker.sock`. Разрешены только `/config`, `/etc/localtime:ro`
  и, если существует системный сокет, `/run/dbus:ro`. Произвольных mount/device/command
  полей для манифестов не добавлено.
- Root-helper сохраняет `RestrictAddressFamilies=AF_UNIX`. Он читает TCP-таблицы
  procfs для проверки порта; HTTP health-check выполняется внутри контейнера.

`privileged` сам по себе даёт широкий аппаратный доступ. Отсутствие docker.sock не
делает такой контейнер безопасным для недоверенного кода или custom integrations.

## Данные

Защищённый каталог на хосте:

```text
/var/lib/home-ai-modules/homeassistant.module/
  active.json              # текущие image digest и каталог конфигурации
  config/                  # начальная конфигурация, монтируется как /config
  config-<номер>/           # отдельные поколения конфигурации после обновлений
  backup-config-<номер>.json # digest и исходный каталог перед обновлением
```

Пути задаёт helper, не браузер. Каталог принадлежит root; секреты конфигурации не
становятся доступными сервисному пользователю HomeAiCore. Символические ссылки в
корне хранилища запрещены. Копирование конфигурации отклоняет ссылки и специальные
файлы, вместо чтения данных за пределами `/config`.

Удаление модуля сначала останавливает контейнер, затем удаляет **только контейнер**.
Конфигурация, запись активного поколения и резервные поколения остаются. Повторная
установка поверх сохранённых данных требует того же digest: другая версия не должна
незаметно выполнять миграции. Используйте сохранённый manifest с точным digest, затем
обычное обновление из каталога.

Резервные поколения автоматически не удаляются. Следите за свободным местом.
Внешние базы данных и данные других контейнеров этим механизмом не копируются.

## Релизы и digest

Каталог должен явно содержать опубликованный модуль. При проверке каталога Core
обращается к `home-assistant/core/releases/latest`, исключает draft/prerelease,
получает anonymous pull token для фиксированного официального GHCR-репозитория,
скачивает manifest index и сверяет SHA-256 его байтов с `Docker-Content-Digest`.
Архитектуры берутся из Linux platform descriptors. Private catalog PAT туда не передаётся.

Предлагается только более новая версия. Изменение digest уже опубликованной версии
не принимается молча. При недоступности upstream сохраняется закреплённый образ
каталога и выводится предупреждение; контейнер самостоятельно не обновляется.

После `docker pull` helper дополнительно проверяет платформу скачанного образа и
наличие запрошенного digest в `RepoDigests`. Проверка digest — контроль целостности
и фиксация содержимого, **не проверка криптографической подписи издателя**.

Для подготовки новой записи каталога сопровождающим проекта:

```sh
go run ./cmd/home-ai-ha-manifest > /tmp/homeassistant-manifest.json
```

Команда только получает метаданные и печатает Manifest v2. Она ничего не устанавливает
и не публикует. `packaging/homeassistant/manifest.json` — закреплённый manifest,
подготовленный при добавлении интеграции; каталог опубликованных модулей хранится
в `DeadSoulf/home-ai-core_modules`.

## Ручное обновление и откат при ошибке

1. Сначала скачивается и проверяется новый digest; работающий контейнер не изменяется
   при ошибке загрузки или несовместимости платформы.
2. Старому контейнеру даётся до 60 секунд на остановку. Копирование начинается только
   после проверки, что он больше не работает.
3. Вся `/config`, включая SQLite и WAL-файлы, копируется в **новое поколение**.
   Требуется место для полной копии плюс резерв 256 MiB. Старое поколение не изменяется.
4. Кандидат запускается с копией. Проверяется HTTP на `127.0.0.1:8123/` через Docker
   health-check; на первый запуск отводится до пяти минут.
5. Старый контейнер сохраняется остановленным до записи нового manifest в реестр Core.
   При ошибке запуска, проверки, смены имени или записи реестра выполняется компенсация:
   кандидат останавливается и удаляется, возвращаются **старый образ и исходная база**.
6. После фиксации реестра обновляется `active.json`, старый контейнер удаляется;
   исходная конфигурация остаётся резервной копией.

Восстановление использует неизменные container IDs, а не предположение о результате
`docker rename`. Старый экземпляр не запускается, если нельзя подтвердить остановку
кандидата: ошибка восстановления показывается оператору, а не маскируется успехом.

Это компенсация неуспешного обновления, а не интерфейс произвольного downgrade после
успешной миграции. При аварийном отключении питания в середине операции staging-контейнеры
могут потребовать ручного восстановления. Новая операция не перезаписывает такие контейнеры.
Сохраняйте `active.json`, backup metadata и поколения конфигурации; не удаляйте их вслепую.
Внешние эффекты автоматизаций и изменения во внешних БД не откатываются.

## Границы поддержки и проверки

Home Assistant Container не содержит Supervisor и магазина приложений Home Assistant OS.
MQTT, Zigbee2MQTT и подобные службы остаются отдельными контейнерами.
Профиль ожидает стандартный HTTP-порт 8123: изменение порта/HTTPS внутри HA потребует
отдельной доработки health-check и ссылки, а не произвольных параметров из manifest.
Синхронизация сущностей, REST/WebSocket API и управление устройствами AI-агентом в это
изменение не входят.

Автотесты используют изолированный stateful fake Docker: установка/управление/удаление,
сохранение данных, неверный digest, неудачный запуск/health-check, ошибки и потеря ответа
при rename, компенсация ошибки реестра, невозможность остановить кандидата, запрет ссылок,
защита обычной песочницы и резервирование `/config`. Это не аппаратный smoke-test на сервере.

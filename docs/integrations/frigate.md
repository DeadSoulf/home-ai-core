# Frigate: официальный контейнер в HomeAiCore

Интеграция доступна начиная с Core **0.1.211**. Существующие NVR, AI Agent и Home Assistant не заменяются. Frigate скачивается непосредственно из официального GHCR; пересборка или форк Frigate не требуются.

## Установка и управление

1. Обновить HomeAiCore до 0.1.211 или новее, проверив подписи выпуска.
2. Открыть «Модули» → «Доступные», выполнить общую проверку обновлений.
3. Выбрать Frigate, проверить версию, архитектуру, полный digest и предупреждение о профиле контейнера; подтвердить установку.
4. После успешной задачи открыть Frigate в левом меню. В Core 0.1.213+ доступны штатные Settings → Camera configuration и Config Editor самого Frigate. Управление контейнером и его обновлением остаётся в разделе модулей HomeAiCore.

При первой установке камер нет, MQTT и детекция выключены. Сначала назначьте параметры хранения/retention и проверьте свободное место. Пароли камер находятся только в административном редакторе; они не передаются в URL изображений и не записываются в audit.

Начиная с **Core 0.1.213**, пункт Frigate открывает **полный штатный интерфейс официального контейнера**, а не страницу со снимками. Доступны исходные страницы Live, Review/History, Explore, Export, Settings, System, Logs и Config Editor, включая графические настройки камер, детекции, зон и масок. Установленный Frigate не нужно переустанавливать: после обновления Core используется тот же контейнер и его существующие данные.

Интерфейс встроен в HomeAiCore на отдельном HTTPS-origin; есть открытие в отдельной вкладке. REST, WebSocket, MSE, HLS/VOD, экспорт и Range-загрузки проксируются без прежнего сокращённого allowlist. Старый API bridge сохранён для обратной совместимости. Обновления Frigate и откат по-прежнему выполняются через Core.

### HTTPS-доступ и авторизация

Core дополнительно слушает **8971/tcp** на том же интерфейсе, что основной HTTPS-сервис. Это защищённый шлюз Core, **не опубликованный порт контейнера**. Используются тот же TLS-сертификат и действующая сессия HomeAiCore; требуется `modules.manage`. Каждый запрос проверяется, а длинные потоки/WebSocket перепроверяются каждые 15 секунд и закрываются при отзыве сессии, прав, остановке модуля или Core.

Cookie, Authorization, CSRF-токены и произвольные proxy-заголовки Core в контейнер не передаются. Ответы контейнера не могут устанавливать или очищать cookie Core. Запись и WebSocket с cookie-сессией требуют точного Origin шлюза. Встроенная страница изолирована отдельным origin и sandbox, не получает DOM/localStorage/CSRF главной страницы. Неаутентифицированный контейнерный порт 5000 остаётся внутри Docker.

При конфликте порта используется `HOME_AI_FRIGATE_UI_LISTEN`, например `0.0.0.0:18971`; адрес привязки должен совпадать с Core. Значение `off` отключает шлюз. Отказ занятого порта не останавливает Core и показывается на странице Frigate. Клиентский firewall/reverse proxy должен пропускать выбранный HTTPS-порт. При самостоятельном сертификате доверие браузера нужно подтвердить и для origin Frigate, открыв его отдельной вкладкой. Публичный reverse proxy должен сохранять корректные HTTPS origin/порты обоих сервисов.

### Возможности, которым нужна отдельная настройка

Полный интерфейс не означает автоматическое наличие дополнительного оборудования или сервисов. MSE/live и архив проходят через HTTPS. Для WebRTC и двустороннего аудио нужен доступный ICE/TURN-медиамаршрут go2rtc; текущий профиль не публикует напрямую UDP/TCP 8555. GPU, Coral/USB, MQTT, распознавание, уведомления и Frigate+ требуют соответствующих устройств, конфигурации, моделей, брокера или учётной записи. Этот выпуск не выдаёт отсутствующий аппаратный passthrough за настроенный. Для разрешения микрофона, уведомлений и PWA рекомендуется отдельная вкладка.

## Источник и совместимость

Каталог содержит не устаревающий Docker digest, а декларацию источника:

```json
{
  "id": "frigate.module",
  "name": "Frigate NVR",
  "provider": "github-ghcr-official",
  "repository": "blakeblackshear/frigate",
  "image_repository": "ghcr.io/blakeblackshear/frigate"
}
```

Core принимает только эту фиксированную комбинацию. Произвольные репозитории, адреса registry, команды, mounts и привилегии через каталог не разрешаются. Старые Core, не поддерживающие декларацию, не получают installable manifest Frigate.

Проверяются стабильные GitHub Releases, исключая draft/prerelease. Порядок версий числовой, а не лексикографический. Для текущего профиля разрешён диапазон **>=0.18.2 <0.19.0**. Это политика совместимости адаптера, а не утверждение об испытании всех будущих patch-релизов. Новая minor/major версия отображается в информации об источнике, но требует отдельного пересмотра интеграции.

Поддерживаются Linux amd64 и arm64. Тег amd64 — номер версии; arm64 — номер версии с `-standard-arm64`. Проверяются:

- SHA-256 точных байтов OCI index/manifest, заголовок registry и размер descriptor;
- единственный подходящий Linux platform manifest;
- SHA-256 и размер config blob, его `os` и `architecture`;
- минимальная версия Core и фиксированный контракт модуля;
- фактически скачанная архитектура образа и Docker health-check.

В manifest фиксируется platform digest, а не изменяемый тег. Digest доказывает целостность относительно ответа официального registry; он **не является подписью издателя**. Корень доверия — официальный GitHub/GHCR по HTTPS. GitHub/registry credentials Core в контейнер не передаются. Публичный pull использует пустой временный Docker config.

## Обнаружение и ручное обновление

Проверка выполняется при открытии каталога, по общей кнопке и каждые 5 минут, пока страница модулей открыта. Это не фоновый серверный scheduler и не автоматическая установка. Ответ кэшируется на 5 минут; ручные проверки ограничены интервалом 30 секунд. При недоступности источника сохраняется последняя проверенная информация текущего процесса, показывается stale-статус, кнопки установки/обновления блокируются. Кэш не выдаётся за свежее разрешение на mutation.

Подтверждение передаёт **точные expected_version и expected_image**, показанные пользователю. API заново проверяет официальный релиз/образ. Job повторяет проверку перед Docker-операцией. Изменившийся digest отклоняется, а не незаметно подменяется.

Обновление проходит существующий Job Engine и аудит. Новая версия должна быть строго новее установленной; одинаковая версия с другим digest не принимается. Фоновая проверка никогда не создаёт задачу установки.

## Профиль контейнера и данные

Официальный s6 bootstrap требует root внутри контейнера и записываемый image layer. Это узкое исключение только для `frigate.module`, а не изменение общего SDK v2.

- Отдельная управляемая сеть `home-ai-frigate`.
- Нет опубликованных host-портов, host network, Docker socket, privileged, GPU/USB/device passthrough.
- `cap-drop ALL`; фиксированный минимум CHOWN, FOWNER, SETUID, SETGID, DAC_OVERRIDE, KILL; no-new-privileges.
- `/dev/shm`: 256 MiB; временный cache: 256 MiB; pids-limit: 2048.
- Конфигурация: `/var/lib/home-ai-modules/frigate.module/config` → `/config`.
- Архив: `/var/lib/home-ai-modules/frigate.module/media` → `/media/frigate`.
- `upgrade.json`, проверенная резервная копия и неудачная конфигурация находятся вне mounts контейнера.

Для крупной системы камеры/GPU/выделенные storage-пулы потребуют отдельно проверенного расширения профиля. Настройка NVR-диска существующего Hikvision модуля не переназначается. Следите за свободным местом файловой системы, где расположен каталог Frigate.

Внутренний API на 5000 имеет административные права. Поэтому весь bridge защищён правом `modules.manage`; одного `modules.read` недостаточно для просмотра камер, конфигурации или паролей. Bridge имеет allowlist путей, ограничивает размеры ответов, не следует redirect, не пересылает cookie, bearer/CSRF токены Core или пользовательские proxy headers. HTML/JavaScript модуля не исполняется в origin Core.

## Обновление и откат

1. Скачать и проверить immutable candidate, создать ещё не запущенный контейнер.
2. Остановить старый Frigate, проверить размещение БД внутри `/config`.
3. Скопировать всю конфигурацию, включая SQLite DB/WAL/SHM, проверить SHA-256/размеры/режимы, fsync файлов и каталогов.
4. Запустить candidate с существующими mounts и дождаться настоящего `healthy`.
5. Поменять имена контейнеров и сохранить новый manifest в БД Core.
6. Удалить остановленный предыдущий контейнер после registry commit. Проверенная копия `/config` остаётся до следующего подтверждённого обновления.

Если candidate не стартовал, не прошёл health-check или Core не сохранил новый manifest, новый контейнер удаляется, конфигурация и SQLite восстанавливаются из проверенной копии, запускается предыдущий immutable image. Неудачное состояние сохраняется в `failed-config-<timestamp>` для диагностики. Если откат сам не удался, задача сообщает ошибку и сохраняет журнал/копию; успех не имитируется.

Копия ограничена 8 GiB, журнал — 16 MiB. Требуется место для копии плюс 2 GiB запаса. Символические ссылки и специальные файлы в `/config` отклоняются. БД вне `/config` блокирует обновление. Не меняйте внутренний API-порт.

**Видеозаписи не входят в копию конфигурации.** Откат не отменяет удаления/изменения архива собственной retention-логикой Frigate. Перед значимыми обновлениями нужна независимая резервная копия важных видеозаписей.

### Прерывание питания/процесса

На карточке есть «Восстановить прерванное обновление». Операция идёт через Job Engine, не скачивает новую версию и сопоставляет journal с зарегистрированным digest:

- Core ещё хранит старый manifest: вернуть предыдущий контейнер и проверенную конфигурацию/БД;
- Core уже сохранил новый manifest: проверить здоровый контейнер и завершить cleanup;
- неизвестные images, labels, mounts или несовпадающий journal: остановить восстановление без разрушительных догадок.

Во время незавершённого обновления start/restart/remove блокируются; аварийный stop остаётся доступен. Обычное удаление модуля сохраняет данные. При повторной установке поверх сохранённой обновлённой БД требуется тот же сохранённый image, чтобы не выполнить миграцию без backup. Эта версия не предоставляет произвольный downgrade после завершённого успешного обновления.

## Проверки

Автотесты охватывают official-source allowlist, semver, архитектуру, повреждённые OCI документы, redirects/token isolation, точное подтверждение digest, CSRF/RBAC, stale-кэш, запрет автоматических установок, конфигурацию, SQLite sidecars, ограничение размера, symlink, режимы при UMask=0077, registry commit/rollback и безопасный API bridge.

Реальный opt-in Docker тест:

```sh
FRIGATE_LIVE_TEST=1 go test -v ./internal/frigate -run TestOfficialUpstreamLive -count=1
go test -c -o /tmp/frigate-integration.test ./cmd/home-ai-core-updater
sudo env FRIGATE_DOCKER_TEST=1 /tmp/frigate-integration.test \
  -test.run=TestFrigateDockerLifecycle -test.v -test.timeout=25m
```

Использовать только изолированный Docker host. Тест отказывается трогать существующие Frigate контейнеры/сеть. Он запускает официальный amd64 Frigate 0.18.2; две проверенные immutable ссылки index/platform на один image нужны для проверки транзакции, а не для имитации испытанного будущего релиза. Намеренно изменяется настоящая SQLite и портится YAML, после чего проверяются восстановленное значение и `PRAGMA integrity_check`. Отдельно проверяется прерывание до и после registry commit. Аппаратный arm64 и реальные пользовательские камеры не проверяются этим тестом.

## Проверка полного интерфейса (0.1.213)

`./scripts/test-frigate-native-ui.sh` запускается только на изолированном тестовом Docker host. Используется настоящий официальный Frigate 0.18.2, синтетическое видео FFmpeg, настоящие TLS/cookie-сессии Core и production Web bundle. Проверяются изоляция origin, запрещённый анонимный доступ, воспроизведение MSE с продвижением currentTime, штатные настройки и Monaco, реальные записи/HLS, создание MP4-экспорта и Range-download, сохранение YAML и отзыв доступа после выхода. Тест не использует пользовательские камеры/пароли/базы. В release CI он обязателен вместе с существующими тестами отката.
